\begin{abstract}
This study examines an open-source testbed for a pre-shared-key-authenticated hybrid X25519 and ML-KEM-768 exchange on ESP32. The package combines a FreeRTOS client, a Python HTTP server, a native C key-encapsulation component, and scripts for inspecting archived measurements. It exposes transcript encoding, key derivation, telemetry framing and measurement boundaries for reuse in embedded networking research. Reanalysis of 100 archived handshakes on an ESP32-D0WD-V3 at 160~MHz gives a mean instrumented latency of \BenchmarkMeanMs~ms, sample standard deviation of \BenchmarkSdMs~ms and 95\% confidence interval of \BenchmarkLowMs~to~\BenchmarkHighMs~ms. All recorded observations are retained. The broader elapsed-cycle interval averages \BenchmarkCyclesM~million cycles. An independent 13.8~KB allocation report is distinguished from campaign snapshots, which do not establish a transient heap peak. The archive includes source, serial records, statistical analysis, self-consistency tests and a bounded symbolic model. Historical measurements do not validate later harness corrections. Shared traffic keys across telemetry directions, incomplete historical build provenance and unevaluated side-channel behavior constrain security and performance conclusions. The software provides an inspectable research prototype for studying this integration; it does not introduce a new cryptographic primitive or establish production readiness.
\end{abstract}
\begin{IEEEkeywords}
ESP32, ML-KEM, X25519, FreeRTOS, Reproducibility, Telemetry.

\section{Introduction and research scope}
Embedded post-quantum experiments need more than primitive timing: readers must be able to inspect the network messages, authentication assumptions, task configuration and boundaries of the measurements. The released software~\cite{software} exposes those elements for an application-layer exchange on an ESP32-D0WD-V3 at 160~MHz. It integrates X25519~\cite{b19} and ML-KEM-768~\cite{b2} with a FreeRTOS client and an asynchronous Python HTTP server. Its contribution is the reusable implementation and associated evidence, rather than a new KEM or a claim that PQC first became feasible on ESP32.

X-Wing already combines X25519 and ML-KEM-768 with its own combiner and security analysis~\cite{b41}. Embedded TLS implementations~\cite{b11} and a 2026 ESP32 DTLS/CoAP preprint~\cite{b42} also establish relevant prior feasibility. The latter uses a different clock, RTOS, parameter set and authentication configuration. These differences prevent a direct performance ranking. Our testbed exposes a PSK-authenticated HTTP exchange for inspection and modification under controlled laboratory conditions. Neither X-Wing's proof nor TLS security properties transfer automatically to this construction.

The package is useful for examining binary transcript framing, measurement placement and the distinction between historical hardware observations and current host checks. Supplementary Material S1 retains the extended technical analysis and historical comparisons. Supplementary Material S2 contains the source, evidence and reproduction instructions from the frozen software version cited in Section~\ref{sec:availability}. Separate data acquisitions remain explicitly identified.

\subsection{Research questions and study design}
The study addresses two questions: what instrumented latency and elapsed-cycle behavior are supported by the archived hybrid campaign, and which protocol and measurement properties can be reproduced from the released implementation and evidence? We examine one ESP32 platform and one archived campaign. The analysis retains every recorded observation, identifies the measurement intervals in the source, and distinguishes observations from symbolic and host-level checks. It is a descriptive implementation study; it does not test a causal performance advantage over TLS or establish a new cryptographic construction.

The configuration defines classical, PQC-only and hybrid modes, but the principal archived campaign examined here is hybrid. The current application invokes 100 hybrid attempts, then continuous telemetry. The configured task stack is 32,768 bytes. Stack capacity, stack high-water readings, static memory and dynamic heap allocations are distinct quantities. The archived campaign records ESP-IDF v5.5; its complete build configuration and exact firmware binary are not available.

\subsection{Handshake encoding and key derivation}
The client sends one binary request to \texttt{/handshake}. Table~\ref{tab:messages} gives the hybrid body fields. HTTP headers and TCP/IP overhead are excluded from the listed lengths. The application exchange has one request and one response after transport establishment. The campaign creates and cleans up an HTTP client per handshake; persistent connection reuse is not established.

\begin{table}[htbp]
\caption{Hybrid application-body encoding, in transmission order.}
\label{tab:messages}
\centering\small
\begin{tabularx}{\columnwidth}{lXr}
\toprule
Body & Fields and byte lengths & Total\\
\midrule
Request & Mode (1), client X25519 public key (32), KEM public key (1,184), HMAC (32) & 1,249\\
Response & Session ID (16), server X25519 public key (32), KEM ciphertext (1,088), HMAC (32) & 1,168\\
Telemetry & Session ID (16), IV (12), ciphertext (variable), GCM tag (16) & Variable\\
\bottomrule
\end{tabularx}
\end{table}

HMAC-SHA256~\cite{b24} authenticates the request's first 1,217 bytes. The response HMAC covers those same unsigned request bytes followed by the response's Session ID, server public key and KEM ciphertext. It excludes both authentication tags. Verification therefore binds the server response to the current client parameters. The server authenticates possession of the PSK in the request; confirmation that the client derived the same traffic key arrives through valid telemetry, without a separate client-finished message.

The shared input is the 32-byte X25519 secret followed by the 32-byte KEM secret. HKDF-SHA256~\cite{b20} produces 32 bytes using salt \texttt{HybridPQC-ESP32-Session-v1} and info \texttt{session-key}. The PSK authenticates the transcript and is not input entropy to HKDF. The published evaluation PSK is public and offers no private-credential authentication to someone who can read the repository. A security experiment must provision private credentials separately.

The server creates the 16-byte Session ID using Python's \texttt{secrets.token\_bytes(16)} and the operating-system CSPRNG. The client uses ESP-IDF randomness for its local operations; true-random output depends on the documented entropy-source conditions~\cite{b43}. A Session ID is an identifier, not a substitute for transcript authentication.

\subsection{Telemetry and task lifecycle}
Telemetry uses AES-256-GCM~\cite{b22} without additional authenticated data. Its 12-byte IV contains a four-byte counter followed by eight random bytes. The server checks that received request counters advance. After 50 successfully processed telemetry responses, the client leaves the loop, cleans up the context and starts a fresh handshake. The archived rotation trace supports historical behavior, not execution of the later corrected firmware.

Both directions currently use the same traffic key. Counter checks do not bind a message to a sending role, so directional reflection and cross-direction replay remain limitations. The software is intended for protocol inspection and laboratory evaluation. It should not be used as a secure Internet deployment without redesign and validation of these boundaries.

\section{Reproduction methods and implementation checks}
The code is distributed under the repository's MIT license; dependency licenses remain applicable. The native host build uses a Linux/macOS-compatible C toolchain and Make. Python dependencies are listed in \texttt{server/requirements.txt}. ESP32 reproduction requires ESP-IDF v5.5, a suitable board and a reachable Wi-Fi/server configuration. Commands and metadata requirements are supplied in \texttt{docs/reproduction\_steps.md} and S2.

\begin{enumerate}
\item Check out the exact frozen source version. Recompute historical statistics using the check mode of \texttt{tools/analyze\_submission.py}, as documented in the reproduction guide. This compares numerical records with the UART trace and verifies the generated manuscript values.
\item Build the native library with \texttt{make -C firmware/components/mlkem768}. Install the declared Python requirements, then run \texttt{python3 -m unittest discover -s tests} and \texttt{python3 tools/test\_mlkem768\_kat.py}.
\item Start \texttt{python3 server/server.py} on its default port 8443. Configure local Wi-Fi and server settings in the ignored \texttt{wifi\_config.local.h}; keep private credentials out of published files.
\item In an ESP-IDF terminal, select target \texttt{esp32}, build, flash and capture the full serial output. Preserve the exact commit, toolchain, configuration, ELF/map and binary hashes. Retain all attempts and failures, rather than selecting only completed fast runs.
\end{enumerate}

The legacy \texttt{test\_mlkem768\_kat.py} filename is retained for compatibility. It checks fixed-seed and randomized round trips and modified ciphertext behavior. It does not compare authoritative external expected-answer vectors and does not establish NIST certification. Current Windows host checks exercise both server entry points' framing/HMAC behavior with a substituted KEM output, and missing-library failure behavior. These checks passed in the preparation environment; they are not native KEM or hardware measurements. Full native-library tests require a compatible toolchain and runtime.

The current harness preserves attempted-run identifiers and computes successful-sample statistics separately. It also removes invalid watchdog-reset calls from an unsubscribed task. Host regression checks address failure accounting, but do not validate scheduling or watchdog behavior on an ESP32. A new hardware campaign must be saved separately if these later corrections are to be called physically validated.

\section{Archived results and validation boundaries}
Table~\ref{tab:results} summarizes the reanalysis of 100 archived hybrid handshake records~\cite{dataset}. All logged observations, including the latency tail, are retained. The instrumented latency sums two \texttt{esp\_timer\_get\_time()} intervals covering key generation and network exchange plus response processing. Intervening packing, logging and heap sampling are excluded. The broader CCOUNT interval includes waits and instrumentation and measures elapsed cycles, rather than isolated processor work. Subtracting these intervals would not yield a valid estimate of networking overhead.

The confidence interval uses Student's $t$ distribution with 99 degrees of freedom and sample SD. It assumes independent observations within this campaign and does not quantify variability across devices or environments. The 100 completed records describe the archived acquisition window; they do not establish the later harness's all-attempt success rate. The archive contains 100 watchdog API ``task not found'' errors, disclosed separately from handshake completion.

Independent heap profiling reported a 13.8~KB allocation, excluding the configured task stack and static storage. Campaign snapshots average 22.24 bytes and reach 440 bytes, but miss transient allocations; neither figure should be called a measured handshake peak. Primitive timings, manual electrical notes and TLS traces were collected separately. They do not form a controlled, authentication-equivalent efficiency comparison. Energy values derived from fixed windows are not synchronized power integrals.

Archived ProVerif output~\cite{b25} establishes encoded client/server payload confidentiality and client-to-server injective agreement under idealized operations and an uncompromised private PSK. It does not query later PSK disclosure, reverse authentication, concrete GCM nonces or physical memory exposure. Selected client-buffer zeroization is not evidence of complete server-side erasure or resistance to a live memory dump. Empirical side-channel resistance remains unevaluated.

The recorded firmware version is \texttt{v2.0-mlkem768-final-6-g45d5f57-}; its ELF digest is truncated. An exact historical binary-to-source mapping is unavailable. Synthetic PCAP illustrations cannot repair that provenance gap or replace missing wire captures. The processed endurance CSV is supplied, but its parser's original master input is absent. A separate accepted-row summary and evidence correction note are provided; they do not establish the original attempt denominator or uninterrupted stability. S1 and S2 preserve these distinctions instead of presenting separate acquisitions as one experiment.

\section{Discussion and conclusions}
The testbed provides source-level access to the PSK-authenticated exchange, its telemetry lifecycle and its historical measurement analysis. Researchers can reuse its encodings and analysis interfaces to study implementation changes while preserving acquisition provenance. A new experiment should identify its own build, failures and raw observations, and use matched authentication and instrumentation when comparing protocol costs.

The historical campaign yields a mean instrumented latency of \BenchmarkMeanMs~ms and mean elapsed CCOUNT of \BenchmarkCyclesM~million cycles on the stated ESP32 setup. These observations support inspection of one prototype. Direction-separated traffic keys, stronger implementation correctness checks and controlled memory/energy measurements are necessary for stronger security or efficiency claims. No production-readiness, first-implementation or new-primitive claim is made.
